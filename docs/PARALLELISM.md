# 병렬화 계획

*2026-08-23 · 아직 **아무것도 구현하지 않았다.** 근거와 제안, 그리고 재는 방법이다.*

`--thinking off` 로 텍스트 단계가 767초 → 43초가 되면서 병목이 옮겨 갔다. 이제 시간을
먹는 것은 **판독·전사(②)** 이고, 그 구간은 서로 완전히 독립인 요청 수백 개다. 그런데
우리는 그걸 한 번에 하나씩 보내고 있다.

## 2. GPU에 여유가 있는가

LLM 추론은 성격이 반대인 두 국면으로 나뉜다.

**프리필**(프롬프트·이미지를 읽는 단계)은 큰 행렬곱이라 GPU가 잘 찬다.
**디코딩**(토큰을 하나씩 뱉는 단계)은 배치 1에서 처참하게 논다 — 토큰 하나마다 모델
가중치를 HBM에서 통째로 읽는데, 읽은 바이트당 산술 연산이 거의 없다.

측정된 생성 속도에 토큰당 읽어야 할 가중치를 곱해 실효 대역폭을 추정해 보면:

| 모델 | 구조 | 실측 | 토큰당 가중치 *(추정)* | 실효 대역폭 *(추정)* |
|---|---|---|---|---|
| q38-uncens | **밀집** 27B Q8 | 27 t/s | ~31 GB (전부) | **~840 GB/s** |
| qwen-vl | MoE 35B-A3B Q8 | 66 t/s | ~3.2 GB | ~210 GB/s |
| gemma | MoE 26B-A4B Q4 | 91 t/s | ~2.4 GB | ~220 GB/s |

밀집 모델은 대역폭을 거의 다 쓰는 영역에 있는데 **우리가 쓰는 MoE 둘은 그 1/4에
머문다.** MoE는 전문가마다 작은 행렬곱으로 쪼개져 배치 1에서는 커널을 못 채운다.
→ **여유가 있다.**

> 활성 파라미터 수는 추정이고 어텐션·임베딩·공유 전문가는 항상 읽히므로 실제 MoE
> 대역폭은 이보다 높다. 절대값은 믿지 말 것. **밀집과 MoE 사이의 4배 격차**가 논지다.

### 배치가 왜 이기나

노는 유닛에 다른 일을 주는 것보다 낫다. **가중치를 한 번 읽어 N개 요청이 함께 쓴다.**
가장 비싼 부분(HBM 왕복)을 나머지가 공짜로 얻어 탄다. 그래서 4개 동시 처리가 1개의
4배가 아니라 1개와 비슷한 시간에 끝난다. llama.cpp에 `--parallel` 이 있는 이유다.

### 다만 우리 워크로드는 프리필 쪽으로 기울어 있다

크롭 전사 실측: 박스당 **프롬프트 1,255 토큰 / 생성 41 토큰**.

생성 41토큰은 66 t/s에서 약 0.6초. 그런데 실제로는 박스당 2.16초가 걸린다.
**나머지 1.5초(70%)는 토큰 생성이 아니다** — 이미지 인코딩(mmproj), 프리필, 요청 오버헤드다.

배치가 가장 크게 이기는 곳은 디코딩인데, 여기서는 디코딩이 30%다. 아마달의 법칙이
그대로 적용된다. 다만 프리필과 이미지 인코딩도 여러 요청을 겹쳐 태울 수 있고,
HTTP·토큰화·스케줄링 같은 고정 비용은 다른 요청의 GPU 작업과 겹친다.

**그래서 배수를 예측하지 않는다. 재야 안다.** (§6)

## 3. `--parallel N` 만으로는 아무 일도 일어나지 않는다

이게 핵심이고, 처음 제안에서 빠졌던 부분이다.

`config/models.ini` 의 `parallel = 1` 을 N으로 올리면 **서버에 슬롯이 N개 열린다.**
그런데 `vlm/read_texts.py` 는 `for` 루프로 요청을 하나씩 보낸다 —
앞 요청의 응답을 받아야 다음 요청을 만든다. 클라이언트가 한 번에 하나만 띄우면
슬롯 N−1개는 계속 빈다.

```
지금:   [요청1]──응답──[요청2]──응답──[요청3]──응답 ...
목표:   [요청1]┐
        [요청2]├─ 한 배치로 함께 ──응답 3개
        [요청3]┘
```

**서버 설정과 클라이언트 동시성은 반드시 짝으로 가야 한다.** 하나만 바꾸면 효과가 0이다.

한편 "read_page와 read_texts를 한 큐로 합친다"는 처음 제안에 넣었지만 **불필요**하다.
`read_texts` 혼자 692개 독립 요청이라 슬롯을 채우고도 남는다.

## 4. 무엇이 절대 겹칠 수 없는가

```
① Magi ─── 챕터 전체 필요 (배치 클러스터링)
   │
   ├─→ ② read_page   페이지끼리 독립 ※
   └─→ ② read_texts  박스끼리 독립          ◀── 병렬화 대상
            │
        ③ 병합 (순수 계산, 0초)
            │
            ▼  ◆ 여기서부터 직렬. 챕터 전체 전사가 있어야 시작조차 못 한다
        ④ cast (1콜) ── 인물 정규화 + 줄거리를 한 번에 낸다
            ▼
        ⑤ 시트 (1콜) ── cast의 인물 목록이 필요
            ▼
        ⑤ 번역 ────── 시트와 줄거리가 둘 다 필요
            │           단, **배치끼리는 서로 병렬 가능**
            ▼
        ⑥ 검사 (항목별 독립) → ⑨ 조판 (페이지별 독립, CPU 전용)
```

※ 파이프라인이 `--no-cast-memory` 로 부르기 때문에 페이지가 독립이다. 그 플래그를
빼면 페이지 N이 1..N−1의 인물 명부를 받아 **순차 의존이 생긴다.**

**직렬 3단(④ → ⑤시트 → ⑤번역)은 우회 대상이 아니라 설계 그 자체다.** 1순위가 맥락
유지이고, 챕터를 관통하는 화자 동일성과 말투는 전체 전사를 한 번에 봐야 나온다.
다행히 `--thinking off` 이후 이 구간은 43초로 작다.

## 5. 제안 — 순위와 예상 효과

### 1순위: ② 크롭 전사 동시 요청 *(핵심)*

- **서버** `config/models.ini` 의 `parallel = 1` → 4 (전 섹션)
- **클라이언트** `vlm/read_texts.py` 의 순차 루프를 `ThreadPoolExecutor(max_workers=N)` 으로

VRAM은 거의 안 는다. llama.cpp의 `--parallel N` 은 `ctx-size` 를 N 슬롯으로 **나눠**
쓰므로 총 KV는 그대로다. 크롭 요청은 프롬프트가 1~2K 토큰이라 65536/4 = 16384
슬롯이면 충분하고도 남는다.

주의할 것:
- 출력 순서가 섞이므로 진행 로그를 `[i/n]` 로 유지하려면 인덱스를 함께 넘겨야 한다
- 실패 격리를 유지해야 한다. 지금은 박스 하나가 실패해도 나머지가 진행된다
- `--limit`, `--pages` 같은 기존 필터와 충돌하지 않아야 한다

### 2순위: ② 페이지 판독 동시 요청

같은 방식. 8~77개 요청이고 이미지가 커서(전송 1088×1536) 프리필 비중이 더 크다.
1순위 결과를 보고 판단한다.

### 3순위: ⑤ 번역 배치 동시 요청

번역은 이미 배치로 쪼개져 있고(`--batch-lines 60`) 배치끼리 독립이다.
**디코딩 비중이 높아 배치 이득이 가장 클 구간**이다 — 배치마다 출력이 수천 토큰이다.
다만 `--batch-overlap` 이 직전 배치의 원문을 맥락으로 쓸 뿐 결과를 쓰지는 않으므로
동시 실행에 문제가 없다.

### 4순위: ⑨ 조판을 GPU 작업과 겹치기

조판은 CPU 전용(OpenCV/PIL)이라 다음 챕터의 GPU 작업과 완전히 겹칠 수 있다.
다만 51초짜리라 순위가 낮고, 챕터를 연달아 돌릴 때만 값을 한다.

### 하지 않을 것

- **`--parallel` 만 올리기** — 클라이언트가 순차라 효과 0 (§3)
- **read_page/read_texts 큐 합치기** — 불필요 (§3)
- **④⑤ 직렬 구간 쪼개기** — 설계 위반 (§4)

## 6. 어떻게 잴 것인가

`tools/bench_models.py` 가 이미 예열로 적재 시간을 빼고 초와 토큰을 함께 잰다.
여기에 동시성 축을 더한다.

```
고정: ep11_cn magi.json (34박스), qwen-vl, thinking off
변수: (server parallel, client workers) = (1,1) (2,2) (4,4) (8,8)
재는 것: ② 크롭 전사 소요, HBM 온도 최고값, 평균 소비 전력
```

`(1,1)` 이 기준선 73.5초다. **(1,4) 도 한 번 재야 한다** — 서버 슬롯 없이 클라이언트만
동시로 보내면 어떻게 되는지가 §3 주장의 대조군이다.

판정: 소요가 줄지 않으면 프리필 지배가 맞고 이 방향은 접는다. 줄면 어디까지
스케일하는지 본다.

## 7. 이 하드웨어의 제약 — 공짜가 아니다

**전력은 올라간다.** 놀던 유닛이 일하면 순간 소비가 180W 제한에 붙어 있게 된다.
토큰당 에너지는 내려가고(가중치 읽기를 N개가 나눠 쓰므로) 총 작업 시간도 줄어
**작업 전체의 에너지는 줄지만**, 순간 발열은 늘어난다.

CMP 170HX는 **패시브 히트싱크 마이닝 카드**다. 2026-08-23 에 약 40분 연속 100%
부하 뒤 `Xid 79 — GPU has fallen off the bus` 로 카드가 사라져 재부팅했다.
`~/Developments/170hx_maintenance/CMP170HX_유지관리_주의사항.md` 는 전력제한 180W +
팬 최대, HBM 80°C 미만을 요구한다.

→ **동시성 실험은 HBM 온도를 함께 감시하며 짧게 끊어 돌린다.** 이득이 20%인데
카드를 잃으면 손해다.

## 8. 미해결 질문

- **프리필 대 이미지 인코딩 비중.** 박스당 1.5초가 토큰 생성이 아닌데, 그중 mmproj
  이미지 인코딩이 얼마인지 모른다. 이미지 인코딩이 지배적이라면 동시성보다 **크롭
  해상도**(`--min-side 896 --max-side 1536`)를 손대는 쪽이 효과가 클 수 있다.
- **동시 요청이 정확도를 건드리는가.** 배치 안에서 숫자 연산 순서가 달라지면 결과가
  비트 단위로 달라질 수 있다. `temperature 0` 이라도 배치 크기에 따라 출력이 바뀔 수
  있으므로, 동시성을 켠 뒤 문자 정확도를 다시 재야 한다 (`--thinking off` 기준 98.2%).
- **단일 모델 파이프라인과의 상호작용.** 판독까지 gemma로 내리면 모델 교체가 사라지고
  (§docs/MODELS.md) 챕터를 겹쳐 돌리기도 쉬워진다. 다만 `read_page` 는 전체 페이지를
  보내므로 Gemma의 0.65MP 비전 상한을 먼저 재확인해야 한다 — **아직 안 쟀다.**
