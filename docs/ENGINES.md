## 0. 한 줄

**목표는 vLLM 이 llama.cpp 를 완전히 대체하는 것이다.** 이상적으로는 **모델 하나 ·
서버 하나로 전 단계** — 보유 vLLM 모델 4개가 전부 비전 가능하므로 가능성이 있다.
그러면 모델 교체가 아예 사라진다.

llama.cpp 는 **지우지 않되 폴백으로 격하한다** — 관문(§7.1)이 막히거나 VRAM 이
빠듯할 때만. 엔진은 설정으로 고르고, 파이프라인이 서버의 "원하는 상태" 를
선언적으로 강제한다(§4).

> **별칭 주의.** `qwen-vl` 은 모델 이름이 아니라 우리가 붙인 라벨이다 —
> 실제로는 **Qwen3.6-35B-A3B**(`Q8_K_P.gguf`)이고 판독 두 단계를 맡는다.
> `gemma` 는 **Gemma4-26B-A4B**(`Q4_K_M-MTP.gguf`)이고 텍스트 단계를 맡는다.
> vLLM 쪽 `v-qwen36` 은 **같은 베이스 모델의 다른 양자화**다.

## 1. 왜 옮기나 — 우리 워크로드가 정확히 vLLM 이 이기는 구간이다

vLLM 학습 문서의 결론표에서 우리에게 해당하는 줄:

| 상황 | 선택 | 실측 근거 |
|:---|:---|:---|
| **긴 입력 배치 (만화, 문서 처리)** | **vLLM** | 프리필 2배 · TTFT 3.2배 · 슬롯 컨텍스트 제약 없음 |
| **동시 요청이 많다 (16+)** | **vLLM** | 디코딩 2.3~4.4배 |
| 1인 1스트림 디코드 | llama.cpp 도 충분 | 격차 1.20배 |
| VRAM 이 빠듯하다 | **llama.cpp** | 같은 8비트에서 39GB vs 58GB · `-ngl` 부분 오프로드 |
| GGUF 만 있는 모델 | **llama.cpp** | 형식 지원이 넓다 |

우리는 첫 두 줄에 정확히 해당한다. 77페이지 챕터는 **크롭 전사 692개 + 페이지 판독 73개**,
전부 서로 독립인 요청이다.

### 그리고 이건 우리가 부딪힌 벽을 직접 없앤다

[PARALLELISM.md §9](PARALLELISM.md) 에서 잰 것: 클라이언트 동시성 이득이 **1.17배에서
멈췄고**, 서버 `--parallel` 을 올려도 차이가 없었으며, 오히려 **해로웠다** —
`n_ctx_slot = ctx-size ÷ 슬롯 수` 라 `parallel=4` 면 16,384 인데 ④ cast 는 프롬프트만
16,786 토큰을 쓴다.

**이 셋은 전부 llama.cpp 고유의 한계였다.** vLLM 은 슬롯을 사전 선언하지 않고 공유 KV
풀에서 필요한 만큼 가져간다. 학습 문서가 같은 벽을 정면으로 기록했다 — llama-server 는
`-c 131,072` 를 줘야 "동시 16 × 8k" 가 됐고, vLLM 은 그런 실패가 한 번도 없었다.

> **§9 의 1.17배는 천장이 아니라 llama.cpp 의 천장이었다.** 다시 재야 한다.

## 2. 무엇을 바꾸는가 — 코드는 거의 안 바뀐다

`vlm/backend.py` 가 이미 엔진을 추상화하고 있고 `config.json` 의 `backends` 는 지금도
4개다. **vLLM 은 다섯 번째 항목이다.** 단계별 모델 배치(`stages`)는 그대로 둔다 —
바뀌는 것은 그 모델이 어느 백엔드에 붙느냐뿐이다.

| 대상 | 내용 | 규모 |
|:---|:---|:---|
| `config/config.json` | `engines` 블록 신설(§3) + `backends` 에 vLLM 항목 | 설정 |
| `config/models.ini` | **llama.cpp 전용이므로 그대로.** vLLM 은 안 읽는다 | 없음 |
| `tools/sync_models.py` | `.ini` 동기화가 vLLM 항목을 지우지 않게 | 소 |
| `vlm/backend.py` | `thinking_style` 에 vLLM 방식, `health()` 를 **모델 이름까지** 확인 | 소 |
| `pipeline.py` | 서버 관리를 **선언적 상태 강제**로 (§4) | 중 |
| `tools/bench_models.py` | 엔진 축 추가 | 소 |

## 3. 바이너리·기동 명령을 설정으로 뺀다

지금 `pipeline.py:40` 에 `LLAMA_DIR` 이 박혀 있다(환경변수로만 덮어쓸 수 있다).
**엔진이 둘이 되면 이 방식은 못 버틴다.** `config.json` 에 `engines` 블록을 신설한다.

```jsonc
"engines": {
  "llamacpp": {
    "bin": "/home/lota/Developments/llamacpp/llama_server_cuda/llama-server",
    "ld_library_path": "/home/lota/Developments/llamacpp/llama_server_cuda",
    "args": ["--models-preset", "{config_dir}/models.ini",
             "--models-max", "1", "--models-autoload",
             "--host", "127.0.0.1", "--port", "{port}"],
    "ready_timeout": 300,
    "multi_model": true          // 라우터라 한 프로세스가 여러 모델을 갈아 끼운다
  },
  "vllm": {
    "bin": "/home/lota/Developments/vllm/run_vllm_server.py",
    "python": "/home/lota/Developments/vllm/.venv/bin/python",
    "args": ["{model_path}", "--port", "{port}", "--util", "{util}",
             "--len", "{max_model_len}", "--kv", "fp8", "--no-eager", "-y"],
    "ready_timeout": 600,
    "multi_model": false         // 프로세스당 모델 하나
  }
}
```

- 경로가 바뀌면 **이 파일만 고친다.** 코드에는 경로가 없다
- `{port}` `{model_path}` `{util}` 같은 자리표시자는 백엔드·모델 항목에서 채운다
- 환경변수 덮어쓰기(`LLAMA_SERVER_DIR`)는 남겨 둔다 — 임시 실험용

## 4. 서버 관리 — 파이프라인이 통제한다 (선언적으로)

앞선 초안에서 "파이프라인이 서버를 관리하지 않는다" 고 썼는데 **그건 잘못된 방향이었다.**
어느 모델을 쓸지 정하는 것은 파이프라인이다. 그러면 그 상태를 맞출 책임도 파이프라인에 있다.

### 원하는 상태를 선언하고, 어긋날 때만 개입한다

단계마다 **원하는 상태**가 config 에서 정해진다: `(엔진, 모델, 포트, util, max_model_len, kv)`.
파이프라인은 매 단계 앞에서 실제 상태를 읽고 비교한다.

```
① 포트에 서버가 살아 있나?            → 없으면 띄운다
② /v1/models 의 이름이 원하는 모델인가? → 다르면 내리고 다시 띄운다
③ 기동 인자가 원하는 설정과 같은가?     → 다르면 내리고 다시 띄운다
④ 전부 같다 → 그대로 쓴다 (아무것도 안 한다)
```

**정상 운용에서는 ④ 로 끝난다.** 서버가 상주해 있으면 파이프라인은 손대지 않는다.
"매 실행마다 기동을 기다린다" 는 걱정은 상태가 어긋났을 때만 현실이 되고, 그때는
**기다리는 게 맞다** — 엉뚱한 모델로 77페이지를 돌리는 것보다 낫다.

③의 "기동 인자" 는 llama.cpp 라우터에서는 이미 `/v1/models` 응답의 `status.args` 로
읽을 수 있다(실측 확인). vLLM 은 `/v1/models` 가 인자를 주지 않으므로 **우리가 띄울 때
기동 인자를 사이드카 파일로 남기고** 그걸 비교한다.

### ★ health 200 만 보면 안 된다

지금 `Client.health()` 는 `/v1/models` 가 200 이면 통과다. **학습 문서의 측정 함정
목록에 이것 때문에 생긴 사고가 두 건 있다** — 새 서버를 기다리다 *옛 서버*의 200 을
보고 통과했고, 기동 실패했는데 이전 서버가 살아남아 그걸로 측정했다.

→ **모델 이름까지 대조한다.** 이건 vLLM 도입과 무관하게 지금도 고쳐야 하는 결함이다.

### llama.cpp 는 지금 동작을 유지한다

라우터 모드는 온디맨드 교체를 하므로 "모델이 다르면 재기동" 이 필요 없다.
`multi_model: true` 로 구분해 ②③을 건너뛴다.

## 5. 기동 시간의 정체 — PCIe 가 주범이 아니다

학습 문서의 측정에서 분해할 수 있다:

| 구성 | 기동 |
|:---|---:|
| AWQ · **eager** · util 0.94 | **88 s** |
| AWQ · **no-eager** · util 0.94 | **271 s** |
| 같은 것, 컴파일 캐시 히트 | **106 s** |
| *(그중 `torch.compile` 만)* | *77.8 s* |

읽어낼 것:

- **eager 88초 ↔ no-eager 271초.** 차이 183초가 전부 **`torch.compile` + CUDA 그래프 캡처**다.
  가중치 적재와 무관하다
- **콜드 271초 ↔ 캐시 히트 106초.** 컴파일 캐시가 165초를 줄인다 → **두 번째 기동부터는
  100초대**다. PCIe 라면 캐시로 줄지 않는다
- 24GB 를 PCIe Gen2 x4(≈1.6GB/s)로 밀면 산술적으로 **15초 남짓**이다. eager 88초의
  일부일 뿐이다

**즉 느린 원인은 전송이 아니라 컴파일이다.** 그래서:

- **상주가 답이다.** 컴파일은 1회성이고 캐시가 남는다
- 손잡이를 자주 돌리는 실험에는 `--eager` (88초)
- 프로덕션은 `--no-eager` — 디코드가 **3.8배** 빠르다(14.4 → 54.7 tok/s)

> 이 분해는 학습 문서의 표에서 **역산한 것**이다. vLLM 은 기동 로그에 
> `Loading weights took`, `torch.compile takes`, `Capturing CUDA graphs took` 를
> 각각 찍으므로, 도입 첫 기동 때 **로그에서 직접 확인해 이 표를 대체할 것.**

### 기동을 기다리는 동안 파이프라인이 할 일 — 있다

| 겹칠 수 있는 일 | 소요 | LLM 서버 필요? |
|:---|---:|:---|
| **① Magi 기하학** | 66s (8p) · 더 큰 챕터면 더 | **아니오** (PyTorch 로컬) |
| 크롭 준비 · 페이지 번호 렌더링 | 수 초~수십 초 | 아니오 |
| 이전 챕터의 **⑨ 조판** | 51s | 아니오 (CPU 전용) |

파이프라인은 지금도 ① Magi 를 LLM 호출보다 먼저 돌린다. **순서만 바꾸면 된다** —
서버를 백그라운드로 띄우고, 그 사이 Magi 를 돌리고, ② 앞에서 준비 완료를 기다린다.
eager 기동(88초)이면 Magi 66초가 대부분을 덮는다.

> ⚠ **한 가지 상호작용.** vLLM 은 기동 중 **남은 VRAM 을 재서** KV 풀 크기를 정한다.
> 그때 Magi 가 2GB 를 쥐고 있으면 풀이 그만큼 작아진다. 실패는 아니고 결정론적이지만,
> **util 을 그만큼 낮춰 잡거나** 메모리 프로파일링이 끝난 뒤 Magi 를 시작해야 한다.
> 어느 쪽이든 **한 방식으로 고정**해야 측정이 재현된다.

### ~~✗ v-gemma4 는 vLLM 0.27.1 에서 기동하지 못한다~~ *(2026-08-26 — 해소됨, §14)*

```
AmbiguousGlobalPerLayerAttributeError: 'head_dim' is a per-layer attribute
  and may vary across layers.
```

학습 문서가 **다른 Gemma4 저장소(AWQ)에서 겪었다고 기록한 것과 같은 오류**다.
저장소 문제가 아니라 **vLLM 0.27.1 과 Gemma4 의 이종(heterogeneous) 레이어 설정
사이의 문제**로 보인다 — 층마다 `head_dim` 이 다른데 vLLM 이 전역값을 읽으려 한다.

오류 메시지가 우회책을 알려준다(`allow_global_per_layer_attribute_access=True`).
**쓰지 않는다** — 같은 메시지가 "동종 모델을 가정한 코드가 전역값을 잘못 쓸 수 있다"
고 경고한다. 조용히 틀린 결과를 낼 수 있는 우회를 벤치마크의 토대로 삼을 수는 없다.

**결과: 완전 대체를 하려면 텍스트 단계도 Qwen 계열이 맡아야 한다.**
다행히 남은 세 모델이 전부 비전 가능이라 "한 모델로 전 단계" 가 여전히 성립한다.

### 북마크의 판정은 "가설" 로 취급한다

`model_bookmark.md` 의 SM80 판정은 **NVFP4-NVFP4 = 순손실**(A4 를 Marlin 이 버림),
**NVFP4-FP8 = A축 fp8 폴백**, **INT8-INT8 = 선호**다. 우리가 가진 넷 중 둘이 "순손실"
판정을 받은 셈이다.

**그래도 잰다.** 그 판정은 일반론이고, 우리가 재는 것은 **이 워크로드에서의 정확도와
속도**다. 실제로 우리 프로젝트는 "밀집이 MoE 보다 낫다"는 일반론이 이 작업에서
뒤집히는 것을 이미 봤다.

### ⚠ 이전 측정을 소급하지 않는다

엔진과 모델과 양자화가 **동시에** 바뀐다. [MODELS.md](MODELS.md) 의 숫자는
llama.cpp + GGUF Q4~Q8 에서 얻은 것이라 **한 줄도 옮겨 오지 않는다.** 특히:

- "판독은 qwen-vl 유지가 맞다" — 다시 정해야 한다
- "Gemma 는 켜면 망가진다 (97.4 → 81.5%)" — **모델이 바뀌었으므로 다시 재야 한다**
- "밀집은 값을 못 한다" — 대상 모델이 다르다
- "양자화는 이 작업에 영향 없다" — Q4~Q6 구간의 결론이다. NVFP4/INT8 은 미지

기준선으로 남는 것은 **llama.cpp 현행 구성의 수치**뿐이고, 그건 "옮길 만한가" 를
판정하는 대조군으로만 쓴다.

## 7. 측정 계획

### 7.1 관문 — 이게 안 되면 그 단계는 llama.cpp 에 남긴다

| # | 확인 | 방법 | 실패 시 |
|---:|:---|:---|:---|
| 1 | **구조화 출력이 `maxItems`/`maxLength` 를 강제하는가** | `maxLength:10` 에 긴 글 요청 → 정확히 10자인가. `maxItems:2` 에 6명짜리 챕터 → 정확히 2명인가 | 백엔드를 `outlines`/`guidance` 로 교체 후 재시험 → 그래도 안 되면 **텍스트 단계는 llama.cpp** |
| 2 | 추론 끄기가 먹는가 | 같은 프롬프트를 on/off 로 → **생성 토큰 수가 달라지는가** | `--reasoning-parser` 경로 확인. 안 되면 프롬프트로 억제 |
| 3 | 비전이 통하는가 | 크롭·전체 페이지 양쪽 | 해당 모델 탈락 |
| 4 | `min_pixels` 대응 | 큰 세로쓰기 블록이 `EMPTY` 로 오는가 | `--mm-processor-kwargs` 로 맞춘다 |

**1번이 최대 위험이다.** 우리는 여기에 파이프라인 생존을 걸고 있다 —
[PROGRESS §13](PROGRESS.md) 참조. 상한이 없어 시트가 188,360자, cast 의 `notPeople` 이
19,118자까지 폭주했고, llama.cpp 가 GBNF 로 강제하는 것을 실측 확인해서 막았다.
vLLM 의 기본 백엔드(xgrammar)가 그 키워드를 조용히 무시하면 **폭주가 그대로 돌아온다.**

### 7.2 정확도 · 속도 — 전 모델 × 추론 on/off

`tools/bench_models.py` 를 그대로 쓴다. **엔진 축만 추가하면 된다.**

```
소재:  ep11_cn (중국어 34박스) · ep11_ja (일본어 36박스) — 공식판 정답 있음
모델:  v-qwen36 / v-gemma4 / v-qwen38-int8 / v-qwen38-fp4
추론:  off / on
과제:  transcribe (크롭 전사) · text (④인물 + ⑤시트·번역)
재는 것: 문자 정확도 · 완전일치 · 말투 일치율 · 소요 · 생성 토큰 · peak VRAM
```

**1순위 질문이 바뀌었다.** 예전에는 "판독용 최적" 과 "텍스트용 최적" 을 따로 찾았다.
완전 대체를 노리므로 이제는 **"한 모델이 판독과 텍스트를 모두 감당하는가"** 가 먼저다.
→ 살아남은 모델은 **두 과제 모두에서** 재야 한다.

**단계적으로 좁힌다** — 4모델 × 2추론 × 2과제 × 2언어를 다 돌리면 GPU 시간이 몇 시간이다.

1. **1차: 크롭 전사 · 중국어 · 추론 off** — 4모델. 정확도 하위를 떨군다
2. **2차: 살아남은 것 × 추론 on/off** — 과사고 트레이드오프
3. **3차: 살아남은 것 × 텍스트 과제** ← **여기서 "한 모델로 다 되는가" 가 판가름난다**
4. **4차: 일본어 확인 + 동시성 격자** (§8)

### 7.3 측정 규율 — 지난번에 값을 뒤집은 원인들

우리가 겪은 것과 학습 문서가 기록한 것을 합친다. **전부 실제로 값을 뒤집었다.**

| 함정 | 대책 |
|:---|:---|
| **비전 워밍업**이 첫 측정에 붙는다 (1회성 ~30초) | `bench_models.warm_task()` — 과제를 한 번 돌려 버린다. **vLLM 은 컴파일까지 얹혀 더 크다** |
| 출력 길이 미고정 → 처리량 비교 무의미 | `ignore_eos` + `min_tokens` |
| 같은 서버에 벤치 2개 | `/metrics` 의 `num_requests_running` 확인 |
| **모델 라벨 오인** — 기동 실패했는데 옛 서버로 측정 | `/v1/models` 의 **이름까지** 대조 (§4) |
| health 200 조기 통과 | 200 이 아니라 **모델 이름**으로 대기 |

## 8. 병렬화 구성 — 숫자를 다시 정한다

vLLM 은 슬롯 사전 선언이 없다. **클라이언트 동시성만 올리면 되고**, 서버 쪽 상한은
`--max-num-seqs` 다(기본 256).

| 단계 | 요청 수 (77p) | 성격 | 제안 시작값 |
|:---|---:|:---|---:|
| ② 페이지 판독 | 73 | 큰 이미지, 프리필 쪽 | `--workers 8` |
| ② 크롭 전사 | 692 | 프롬프트 1.3K / 출력 41 | `--workers 16` |
| ⑤ 번역 배치 | 12 | **디코딩 지배** | 동시 4~8 *(미구현)* |

근거: 학습 문서의 확장 곡선에서 **디코딩 지배는 동시 64까지 17.5배**, **프리필 지배는
1.5~2.8배에서 멈춘다.** 우리 크롭 전사는 토큰 비율이 30:1 로 프리필 쪽이지만,
학습 문서 ④③ 이 "토큰 비율 13:1 인데 **시간 비율은 1:1**" 이라고 관찰했으므로
실제로는 디코딩 몫이 크다. 그래서 크롭 전사에 더 높은 동시성을 준다.

**⑤ 번역 배치 동시 실행은 지금 구현이 없다.** llama.cpp 에서는 슬롯 ctx 제약 때문에
근거가 약해 3순위로 미뤘는데, **vLLM 에서는 그 제약이 없고 이 구간이 디코딩 지배라
이득이 가장 클 자리다.** 도입과 함께 구현한다.

### 잴 것

```
엔진:    llamacpp(기준선) / vllm
workers: 1 / 4 / 8 / 16 / 32
재는 것: 소요 · 문자 정확도 · HBM 온도 최고 · 평균 전력
```

**정확도를 매번 함께 잰다.** llama.cpp 에서는 크롭 전사가 workers 1↔4 에서 바이트
단위로 동일했지만, vLLM 은 연속 배칭이라 배치 구성에 따라 달라질 수 있다.

> **HBM 온도를 함께 감시할 것.** 2026-08-23 에 40분 연속 부하 뒤 `Xid 79` 로 카드가
> 버스에서 탈락한 적이 있다. 동시성이 오르면 180W 에 붙어 있는 시간이 는다.

## 9. 두 모델 동시 상주 — **한 모델로 안 될 때만**

vLLM 은 프로세스당 모델 하나다. 판독·텍스트를 다른 모델로 쓰려면 서버가 둘이다.
보유 모델로 계산하면 **24G + 18G = 42G**, 실사용 상한 63.4 GiB 에서 KV 둘에 21G 남는다.
`--kv-cache-dtype fp8` 이 공짜라는 것이 실측됐으므로(64k 문맥까지 손실 측정 한계 이하)
우리 컨텍스트 요구(크롭 1.3K · 페이지 5K · cast 17K)에는 넉넉하다.

얻는 것: **모델 교체 소멸**(현행 챕터당 30~60초), **②와 ④⑤가 동시에** 돌 수 있음,
**챕터 파이프라이닝**(챕터 A 의 텍스트 단계와 챕터 B 의 판독을 겹침).

다만 **활성화·CUDA 그래프가 얼마를 더 먹는지는 재봐야 안다.** §7 이 끝나 모델이
정해진 뒤에 손댈 일이다. 한 모델로 전 단계를 커버할 수 있으면 이 절은 불필요해진다 —
**그것도 §7 이 답한다.**

## 11. llama.cpp 를 남기는 이유 — 세 가지 모두 실재한다

1. **VRAM 이 빠듯할 때.** vLLM 은 부분 오프로드를 안 한다 — 전부 GPU 아니면 실패다.
   llama.cpp 는 `-ngl` 로 나눠 얹는다
2. **GGUF 만 있는 모델.** 새 모델은 GGUF 가 먼저 나오는 경우가 많고, 우리 `Q8_K_P`
   같은 비표준 양자화는 vLLM 이 못 읽는다
3. **관문 중 하나가 막힐 때.** 특히 구조화 출력이 안 되면 텍스트 단계는 llama.cpp 에
   남겨야 한다. **단계별로 백엔드를 다르게 줄 수 있는 것이 이 설계의 값이다**

그리고 기동이 빠르다. 손잡이를 자주 돌리는 실험에는 여전히 낫다.

## 13. 관문 실측 — 4개 전부 통과 (2026-08-26)

`v-qwen36` (Qwen3.6-35B-A3B NVFP4-NVFP4) · vLLM 0.27.1 · `--eager --util 0.75 --len 32768`
`--kv fp8` · `--no-tools --no-reasoning` (변수를 줄이려 파서는 껐다)

### ① 구조화 출력 — **강제된다.** llama.cpp 와 동일

| 시험 | 요구 | 결과 |
|:---|:---|:---|
| `maxLength: 10` 에 긴 글 요청 | — | **정확히 10자** (`"The user's"`) |
| `maxItems: 2` 에 과일 8개 요청 | 8개 | **정확히 2개** |
| `maxItems: 40` 에 과일 8개 요청 | 8개 | 8개 (상한이 안 걸린다) |

**이 계획에서 유일하게 "안 되면 설계를 바꿔야 하는" 항목이 해소됐다.**
`backend.bound_schema()` 가 그대로 값을 한다.

### ② 추론 끄기 — 먹는다. 단 조건이 붙는다

`enable_thinking` 은 채팅 템플릿에 9번 등장하고 실제로 동작한다:

| | 생성 토큰 | `<think>` 태그 |
|:---|---:|:---|
| `enable_thinking: false` | 314 | 없음 |
| `enable_thinking: true` | 526 | **있음** |

> ★ **구조화 출력이 걸리면 추론이 물리적으로 불가능하다.** 같은 질문에 스키마를
> 씌우니 on/off 가 13 vs 8 토큰으로 **둘 다 사고 없음**이었다. 문법이 첫 토큰부터
> JSON 을 강제해 사고 블록이 들어갈 자리가 없다.
>
> **우리 추출 단계는 전부 스키마를 쓴다** → 그 단계에서 `--thinking` 은 사실상
> 무의미할 수 있다. llama.cpp 에서 "추론을 켜면 Gemma 가 97.4→81.5% 로 망가진다"
> 고 잰 것이 vLLM 에서 어떻게 나오는지는 §7.2 에서 다시 봐야 한다.

### ③④ 비전 — 통한다. `min_pixels` 손댈 필요 없다

실제 ep11_cn 크롭 3개(가장 큰 것 2481×3062 포함)를 보내 중국어를 정확히 전사했다.
**`EMPTY` 가 나오지 않았다** — llama.cpp 에서 `image-min-tokens = 1024` 로 막던 문제다.
프롬프트 토큰이 이미지 크기에 따라 2,580~7,518 로 자동 조절된다.

### 기동 시간 — §5 의 역산을 실측으로 대체

| 단계 | 소요 |
|:---|---:|
| 가중치 적재 (22.41 GiB) | **67.9 s** |
| 엔진 초기화 (프로파일 · KV 생성 · 워밍업) | **79.7 s** |
| **합계 (`--eager`)** | **≈ 171 s** |

§5 에서 "PCIe 로 24GB 면 15초 남짓" 이라고 추정했는데 **실제 적재는 67.9초**다.
전송만이 아니라 디스크 읽기·포맷 변환이 포함된 값이다. 그래도 결론은 유지된다 —
`--no-eager` 로 가면 여기에 컴파일·그래프 캡처가 얹히므로 **상주가 답이다.**

### KV 캐시 — llama.cpp 의 슬롯 제약이 없다는 것이 수치로

```
GPU KV cache size: 1,862,602 tokens
Maximum concurrency for 32,768 tokens per request: 56.84x
```

llama.cpp 는 `--parallel 4` 면 슬롯당 16,384 토큰으로 **쪼개져** ④ cast(16,786 토큰)가
안 들어갔다. vLLM 은 같은 32,768 요청을 **동시 56.84개**까지 받는다.

### ~~✗ 실패 기록~~ — 해소됨

`v-gemma4` 는 이 회차에 기동조차 못 했다 —
`AmbiguousGlobalPerLayerAttributeError: 'head_dim' is a per-layer attribute`.
**§14 에서 해결됐다**(모델 `config.json` 에 `text_config.head_dim` 명시 + `--kv auto`).
그래서 "완전 대체를 하려면 텍스트 단계도 Qwen 계열이 맡아야 한다" 는 결론도 철회한다 —
다만 §14 의 판정은 **말투 때문에** 여전히 Qwen3.8 이다.

### 읽어낼 것

#### ① 두 지표가 서로 다른 모델을 가리킨다 — 그리고 그게 이 표의 전부다

**전사는 사실상 평평하다** (93.8 ~ 99.1%). **말투는 38 ~ 94% 로 벌어진다.**
즉 모델 선택의 실질은 전사가 아니라 말투다.

- **전사 1위 = Qwen3.6 계열** (99.1% · 완전일치 93%) 인데 **말투가 38~52% 로 붕괴**한다
- **말투 1위 = Qwen3.8 계열** (90~94%) 이고 전사는 0.3%p 뒤진다
- **Gemma4 는 가장 빠른데 전사가 가장 약하다** (LLM 49~57초 / 93.8~96.2%)

같은 베이스 모델의 양자화 차이(`v-qwen36` 38% ↔ `v-qwen36-int4` 52%)가
계열 간 차이보다 작다. **말투를 가르는 것은 축이 아니라 계열이다.**

#### ② 말투 순위는 표본이 감당하지 못한다

말투 비교 가능 문장이 **16~21개**뿐이다. 90% 와 94% 는 한두 문장 차이다.

결정적 증거가 이 측정 안에 있다: **같은 `v-qwen38-fp4` 가 `--eager` 회차에서 67%,
`--no-eager` 회차에서 94% 였다.** CUDA 그래프는 커널 **제출 방식**만 바꾸는 손잡이다 —
27%p 를 만들 수 있는 물건이 아니다. **그 폭은 전부 잡음이다.**

→ 90% 대 94% 를 순위로 읽으면 안 된다. 38% 대 90% 는 읽어도 된다.

#### ③ `--no-eager` 는 크게 빠르지만 기동을 사서 낸다

| 모델 | `--eager` 파이프라인 | `--no-eager` 파이프라인 | 배수 |
|:---|---:|---:|---:|
| `v-qwen36` | 742s | 164s | **4.5배** |
| `v-qwen38-int8` | 536s | 261s | **2.1배** |

대신 기동이 144~228초로 늘어 8쪽에서는 TOTAL 이 별로 안 준다. **챕터가 길수록
유리해지고, 상주 운용이면 기동은 한 번만 낸다.** §13 의 "상주가 답이다" 를 지지한다.

#### ④ W축 4비트가 A축 INT8 을 이겼다 — 그리고 `vllm/docs` 가 이걸 예측했다

`v-qwen38-fp4` 와 `v-qwen38-int8` 은 **같은 베이스, 같은 크기, 다른 축**이다.

| | LLM 구간 |
|:---|---:|
| `v-qwen38-fp4` (W축 4비트) | 170s |
| `v-qwen38-int8` (A축 INT8) | 203s |
| **W축 우위** | **1.19배** |

[`performance.md`](../../vllm/docs/performance.md) §4.2.6 이 만화 워크로드에서
**동시 4 에 W축 1.22배**를 예측했다. 실측 1.19배 — 오차 2%.

**직관과 반대인 이유는 그 문서 §4.2.6 ③ 에 있다.** 이 워크로드는 토큰 비율이 13:1 이라
"프리필 집약" 으로 보이지만 **벽시계 비율은 최대 1:1** 이다. 출력을 디코딩하는 시간이
프리필보다 길다. 그래서 **W축(메모리 대역폭 → 디코드)이 지배하고, A축(연산 → 프리필)
INT8 은 값을 못 한다.**

덧붙여 `NVFP4-FP8` 의 **FP8 은 A축인데 SM80 에 fp8 텐서코어가 없어 Marlin 가중치
전용으로 폴백한다** ([`quantization.md`](../../vllm/docs/quantization.md) §2).
즉 이 대조는 "NVFP4 A축 vs INT8 A축" 이 아니라 **"W축 4비트 vs A축 INT8"** 이고,
fp8 은 파일 크기(24G vs 30G)에만 기여한다.

> **미측정 공백:** `performance.md` §2.6 은 *"NVFP4 는 Ampere 에서 AWQ 보다 느리고
> 크다 — 고를 이유 없음"* 이라고 못 박는다. 예측대로면 **AWQ 판 Qwen3.8 이 지금 1위인
> fp4 보다 더 빠르고 더 작아야 한다.** 우리는 그 판을 갖고 있지 않아 재지 못했다.
> 지금 순위는 **"가진 것 중의 1등"** 이다.

#### ⑤ "MoE 라서 정확도를 내준다" 는 성립하지 않는다

Gemma4 가 빠른 것은 맞다 — 활성 4B/26B, LLM 구간 49~57초 대 Qwen3.8 의 170~203초로
**3.0~3.6배**다. (활성 파라미터 비 27B/4B ≈ 6.75배에는 못 미친다.)

그런데 **Qwen3.6 도 MoE 다.** 둘의 강점 축이 정반대다:

| | 전사 | 말투 |
|:---|---:|---:|
| Gemma4 (26B-A4B MoE) | 96.2% | **88%** |
| Qwen3.6 (35B-A3B MoE) | **99.1%** | 38% |

Gemma 는 **지각(전사)에서 잃고 생성(말투)을 지키고**, Qwen3.6 은 정확히 반대다.
MoE 구조로는 이 갈림을 설명할 수 없다. **트레이드오프는 구조가 아니라 계열·보정에서 온다.**

같은 축(NVFP4-NVFP4) 의 Gemma4 두 판이 96.2% 대 93.8% 로 갈리는 것이 그 증거다 —
차이는 **제작자뿐**이고, QAT(양자화 인식 학습)를 거친 `llmfan46` 판이 이겼다.
`performance.md` §2.4 가 예고한 *"보정 하이퍼파라미터 민감성 → 제작자마다 다르다"* 의 실례다.

### 판정

**말투가 1순위이므로 `v-qwen38-int8` 또는 `v-qwen38-fp4` 다.** 둘 다 한 모델로
전 단계를 감당하고, **§9 의 "두 모델 동시 상주" 는 필요 없어졌다.**

둘 사이는 **실질 동률**로 본다 — fp4 가 VRAM 6G 적고 LLM 구간 1.19배 빠르지만,
말투 94% 대 90% 는 ② 에서 본 대로 잡음 안이다. **VRAM 과 속도만 확실한 차이이므로
`v-qwen38-fp4` 를 기본으로 둔다.**

### 이전 측정과의 관계

§6 의 ⚠ 규칙대로 [MODELS.md](MODELS.md) 의 숫자는 **옮겨 오지 않는다.** 엔진·모델·
양자화가 동시에 바뀌었고, 채점기도 그 뒤에 두 번 고쳐졌다. 참고로만 적으면 llama.cpp
2모델 구성이 전사 98.2% / 완전일치 81% / 말투 14/17(82%) 였으나, **같은 조건에서 잰
값이 아니므로 위 표와 나란히 두지 않는다.**

### ✓ Gemma4 기동 실패는 해소됐다

§6 · §13 이 기록한 `AmbiguousGlobalPerLayerAttributeError: 'head_dim'` 은 모델
`config.json` 의 `text_config.head_dim: 256` 을 명시해 해결했다. 우회 플래그
(`allow_global_per_layer_attribute_access`) 는 쓰지 않았다 — §6 에서 거부한 그대로다.

이어서 나온 두 번째 벽 `FP8 KV cache is not supported by the Triton attention backend
... compute capability 8.0` 은 **`--kv auto` 를 기본으로 바꿔** 없앴다. 근거는 KV 가
모자란 적이 없다는 것이다 — 실측 1,862,602 토큰(동시 56.8배)인데 실제 수요는
`--workers 16` 이어도 128K 남짓이다. **fp8 KV 는 사는 것 없이 Gemma4 만 막았다.**

## 15. ★ 서버 통제를 버렸다 — 2026-08-27

§4 는 *"파이프라인이 어느 모델을 쓸지 정하므로 그 상태를 맞출 책임도 여기 있다"* 고
썼다. **그 전제를 버린다.** 파이프라인은 이제 **아무 서버도 띄우지 않는다.**

### 왜 뒤집었나 — 근거 두 개가 무너졌다

**① "기동 인자는 HTTP 로 검증할 수 없다" — 틀렸다.**

§4 의 사이드카 파일(`logs/launch-<port>.args`)은 *vLLM 이 자기가 무슨 인자로 떴는지
알려주지 않으니 우리가 기록해 둬야 한다* 는 전제 위에 있었다. 확인해 보니 알려준다:

```
GET /v1/models   →  id · root(실제 경로) · max_model_len          ← 항상
GET /server_info →  VllmConfig 전체 (enforce_eager · kv · util)   ← VLLM_SERVER_DEV_MODE=1
```

프로세스를 소유하지 않아도 검증할 수 있다. 통제를 정당화하던 제일 강한 논거였다.

**② 기동 인자 중 정확성에 걸리는 건 하나뿐이다.**

| 인자 | 성격 | 통제해야 하나 |
|:---|:---|:---|
| `--max-model-len` | **정확성** — ④ cast 가 실측 16,786 토큰 | **확인만.** `/v1/models` 가 준다 |
| `--eager` / `--no-eager` | 속도 2~4.5배 | 아니오 — 결과가 안 바뀐다 |
| `--kv` · `--util` | VRAM·용량 | 아니오 |
| `--no-tools` · `--no-reasoning` | 거동 | 아니오 — 스키마로 강제된다 |

추론 on/off·JSON 스키마·이미지는 **요청 단위**, `--workers`·`max_image_pixels` 는
**클라이언트 단위**다. 기동과 무관하다.

> **그럼 왜 지금까지 통제했나 — 측정하고 있었기 때문이다.**
> 6개 모델 × eager 조합을 재려면 파이프라인이 서버를 갈아 끼워야 했다. §14 로 그
> 캠페인은 끝났다. **요구사항은 벤치마크의 것이었지 파이프라인의 것이 아니었다.**

### 무엇이 바뀌었나

| | 전 | 후 |
|:---|:---|:---|
| `pipeline.py` | 서버를 띄우고·죽이고·VRAM 반환을 기다림 (745줄) | **붙기만 한다** (534줄) |
| 로컬/원격 분기 | `health()` 가 주소로 갈라짐 | **없다.** 전부 OpenAI 호환 주소 하나 |
| `config.json` | `engines`(바이너리·기동 인자) + `stage_presets` + `default_engine` | `backends`(주소록) + `models` + `stages` |
| 외부 프로젝트 의존 | vLLM 바이너리 경로 · 모델 디렉터리 | **없다** |
| CLI | `--engine` · `--eager/--no-eager` · `--no-manage-router` | **삭제** |
| 이식성 | `ss` · `/proc` · `killpg` · `nvidia-smi` → 리눅스 전용 | **코드에서 전부 사라짐** |

파이프라인에 남은 책임은 셋뿐이고 전부 GET 하나로 끝난다:

```
① 그 주소가 우리가 쓸 모델을 실제로 내놓는가
② 컨텍스트가 우리 요청을 담는가        (알려주는 백엔드에 한해)
③ 아니면 무엇을 해야 하는지 말하고 죽는다
```

실제 메시지:

```
백엔드 'vllm' 이 모델 'orcarouter_Qwen3.8-27B_AL_NVFP4-FP8' 을 내놓지 않습니다.
   지금 있는 것: orcarouter_Qwen3.8-27B_AL_INT8-INT8

백엔드 'llamacpp' (http://127.0.0.1:8081/v1) 에 닿지 못했습니다.
   로컬 서버라면 먼저 띄워 주세요 — 이 파이프라인은 서버를 기동하지 않습니다.
```

### 발견 — 파일시스템에서 백엔드로

하루 전(§14 작업 중)에 만든 디렉터리 스캔 발견 계층도 걷어냈다. **무엇이 존재하는지는
백엔드가 안다.** `--list-models` 는 `GET /v1/models` 를 백엔드마다 던져 config 선언과
대조하고, **백엔드에만 있고 config 에 없는 모델까지** 알려준다.

```
별칭           백엔드       상태          컨텍스트  비고
v-qwen38-int8  vllm         사용 가능        32768  Qwen3.8-27B 밀집 INT8-INT8
v-qwen38-fp4*  vllm         미적재                  Qwen3.8-27B 밀집 NVFP4-FP8
qwen-vl        llamacpp     닿지 않음               판독 담당

  백엔드가 내놓지만 config 에 없는 모델: openrouter: … 외 409개
```

vLLM 이 하나만 "사용 가능" 인 것은 결함이 아니라 **프로세스당 모델 하나라는 사실이
그대로 보이는 것**이다 (§13 확인: 베이스 모델 교체 API 가 없다).

### 대가 — 정직하게

| 잃은 것 | 실제 영향 |
|:---|:---|
| VRAM 경합 조정 (`--stop-router-for-magi`) | 서버가 VRAM 을 쥔 채 ① Magi 를 돌리면 OOM 날 수 있다. **이제 사용자가 판단한다** |
| 모델 스윕 벤치 | 스크립트가 서버를 갈아 끼워야 한다. `pipeline.py` 를 루프로 부르기 전에 한 줄 추가 |
| vLLM 에서 판독·텍스트 모델 분리 | 한 번의 실행으로는 안 된다(프로세스당 모델 하나). `--only`/`--from-stage` 로 끊고 그 사이에 서버를 바꾼다. llama.cpp 라우터·원격 API 는 종전대로 한 번에 된다 |
| 원격 백엔드 비용·레이트리밋 | 77쪽을 유료 API 로 돌리면 실제 돈이 든다. `--workers` 가 레이트리밋에 걸릴 수 있다 |

**로컬 모델이 전부 사라진 것은 아니다.** ① Magi(기하)와 `--transcribe ocr` 의
manga-ocr 은 여전히 로컬이고 그대로다 — 둘 다 LLM 이 아니다. 이번에 바뀐 것은
**LLM 백엔드**뿐이다.

### 실제로 겪은 첫 대가 — 같은 날 바로

구조를 바꾸고 첫 E2E 를 돌렸더니 §14 의 `v-qwen38-int8` 행(261s)보다 훨씬 느렸다
(LLM 구간 643s). 원인은 **떠 있던 서버가 `--eager` 였기 때문**이고, §14 의 행은
`--no-eager` 였다 — 이 모델에서 문서화된 2.1배 차이 그대로다.

**파이프라인은 그걸 알 방법이 없었다.** 통제를 놓으면서 같이 놓은 것이 이것이다.

대책은 통제를 되찾는 게 아니라 **보이게 하는 것**이다. 시작 배너가 이제 백엔드가
스스로 밝히는 사실을 찍는다:

```
── 판독 v-qwen38-int8 (vllm · ctx 32768 · cudagraph · kv auto) | 텍스트 …
```

`ctx` 는 `/v1/models` 라 항상 나오고, `cudagraph`/`kv` 는 `/server_info` 라
**`VLLM_SERVER_DEV_MODE=1` 로 띄운 서버에서만** 나온다. 안 나와도 파이프라인은
그대로 돈다 — 진단 편의이지 요구사항이 아니다.

> 품질(전사 98.2%, 말투 70%)도 §14 행(98.8%, 90%)과 달랐지만 **요청 조립 코드는
> 0줄 바뀌었다** — 리팩터가 모델이 받는 것을 바꿀 수 없다. 표본이 각각 28박스·20문장이라
> 차이는 1박스·4문장이고, §14 ② 에서 같은 모델이 67%↔94% 로 흔들린 그 대역 안이다.

### 남는 선택지

한 발 더 가고 싶으면 **모델 교체 프록시**(llama-swap 류)를 로컬 vLLM 앞에 두면 된다.
그러면 vLLM 이 `routing: 다중 · lifecycle: none` 이 되어 OpenRouter 와 구별이 없어지고,
`--list-models` 의 "미적재" 도 사라진다. **파이프라인은 한 줄도 안 바뀐다** — 그게
이 구조의 요점이다.
