## 1. 이 프로젝트가 하려는 것

만화를 **한국어로 자동 역식(번역+조판)** 한다. 우선순위는 사용자가 명시적으로 정했다:

1. **맥락 유지** (챕터 전체를 관통하는 이해)
2. **화자 구분**
3. **말투(존댓말/반말) 개연성** — "그 캐릭터가 할 법한 말투로" 정도의 의미. 정책 엔진 같은 건 필요 없다
4. **일관성** — 반말했다 존댓말했다 하지 않는 것

**타이포그래피·SFX 레터링은 낮은 우선순위다.** 대사가 아닌 것의 처리는 중요하지 않다고 사용자가 못 박았다.

그리고 **사람이 승인하는 단계는 없다.** 파이프라인이 오탐하면 그대로 간다. 대신 명백한 오류는 하드코딩된 결정론적 규칙으로 걸러낸다.

### 소재
`assets/examples/` — 중국어(번체·세로쓰기) 스캔본, 일본어, Pepper&Carrot(공식 다국어판, 정답 대조용).
`assets/secrets/` 는 **절대 열람 금지**(사용자 지시). `assets/groundtruth/peppercarrot` 이 유일한 정답 데이터다.

## 2. 핵심 설계 — 왜 이렇게 되어 있나

### Magi = 기하학만, VLM = 의미 전부

Magi(magiv2)가 VLM 으로 대체 불가능한 것은 **픽셀 정확한 좌표** 하나뿐이다. 지우고 다시 얹을 영역이라 몇 px 도 틀리면 안 된다.

의미(전사·화자·수신자·대사/나레이션 구분·언어)는 전부 VLM 이 맡는다. 이유는 실측으로 확인됐다:

- Magi 의 OCR 은 **영어 전용**이다. 디코더 vocab 50265(RoBERTa BPE)이고 PopManga(Manga Plus 영어판)로 학습돼, CJK 페이지에서 유창한 영어 웹 텍스트를 환각한다. 가중치 로딩 실패가 아니다(1287/1287 키 일치).
- Magi 는 입력을 **흑백으로 변환**한다 → 컬러 소재의 인물 식별 단서인 머리색이 사라진다.
- 인물 클러스터 ID 가 `batch_size` 슬라이스 안에서만 일관된다 → 챕터를 관통하는 동일성은 **캐릭터 뱅크**로만 만들어진다(뱅크 없으면 이름은 전부 `"Other"`).
- `is_essential_text` 로 번역 대상을 거르면 안 된다 — 66개 중 14개만 통과시켜 나레이션·캡션을 날렸다. **화자를 붙일지** 정하는 용도로만 쓴다.

둘을 잇는 방법: **박스 번호를 페이지에 그려 넣고**(박스 바깥에. 안에 그리면 전사가 망가진다) VLM 이 번호로 영역을 지칭하게 한다.

### 2단 구조 — 말투는 페이지 단위로 지킬 수 없다

번역을 시작하기 **전에** 인물별 말투를 한 번 확정하고, 그 시트를 전 페이지에 똑같이 적용한다.
컨텍스트는 **이미지가 아니라 텍스트로** 채운다 — 페이지 이미지는 1~2K 토큰인데, 화자 라벨 붙은 챕터 전사는 66개 박스가 1.5K 토큰이다.

### 반드시 지켜야 할 호출 규약 (실측 근거 있음)

| 규약 | 안 지키면 |
|---|---|
| `response_format: {"type":"json_schema", …}` 강제 | 프롬프트로 부탁만 하면 8페이지 중 5페이지가 파싱 실패. 매번 다른 방식으로 깨진다. 정규식으로 쫓는 건 막다른 길 |
| 추출 단계는 **추론 끄기** (`chat_template_kwargs:{"enable_thinking":false}`) | 추론형 모델이 토큰 예산을 사고에 다 쓰고 `content` 를 빈 채 `finish_reason=length` 로 돌려준다. 끄고도 품질 동일 |
| `--parallel 1`, `cache-type q8_0`, `flash-attn on` | `~/…/llamacpp/run_llama_server.sh` 실측표 근거 |

## 3. 워크플로우와 파일

```
① Magi 기하학          magi/magi_worker.py        → magi.json
   박스·인물·패널·꼬리 좌표 (검출 임계값 0.3)
        │
   ┌────┴──────────────────────┬────────────────────┐
   ▼                           ▼                    ▼
② 판독 2패스                ⑦ 마스크             ⑨ 조판
  vlm/read_page.py            render/make_mask.py    render/bubble.py
   → page.json (화자·언어)     획 단위(연결요소)      말풍선 flood fill
  vlm/read_texts.py           양극성 모두            render/glyph_size.py
   → crop.json (전사)                                투영 프로파일로 글자 크기 실측
  (--fast: ocr/manga_ocr_pass.py)
   │                           │
   ▼                           ▼
③ 병합  vlm/merge_reads.py  ⑧ 인페인팅
   → merged.json               render/compose.py (고전 CV. LaMa 는 아직 불필요)
   크롭 전사 + 페이지 화자, 불일치 플래그
   ▼
④ 인물·스토리  vlm/build_cast.py  → cast.json
   흩어진 화자 라벨을 정규화. 텍스트로만 한다(이미지 4장 넘으면 위치 지목이 무너짐)
   ▼
⑤ 시트+번역  vlm/translate_chapter.py  → styleguide.json (작품 단위), 번역
   vlm/register_cues.py 가 원문 경어 증거를 세어 프롬프트에 주입
   ▼
⑥ 검사·수정  vlm/validate_translation.py
   결정론적 8종 위반 검출 → 걸린 박스만 재요청 (--harsh 는 LLM 판정자, opt-in)
   ▼
⑨ 완성 페이지 → <work>/out/
```

호출 계층: `vlm/backend.py` 가 모든 모델 호출을 모은다. `config/config.json` 의 `stages` 가 단계별 모델을 정하고, `config/models.ini` 가 llama-server 라우터 프리셋이다. **둘은 별개 파일이라 한쪽만 고치면 조용히 어긋난다** — `tools/sync_models.py` 가 `.ini` 를 단일 출처로 `config.json` 을 생성한다.

### 실행

```bash
magi/.venv/bin/python pipeline.py \
  --pages 'assets/examples/maid2/*.jpg' \
  --work work/maid2_full
```

| 옵션 | 뜻 |
|---|---|
| `--fast` | 크롭 전사를 manga-ocr 로. **일본어 전용** (중/영 소재엔 쓰지 말 것) |
| `--skip-pages N …` | 후원자 명단·판권지 제외 (1-base). **판독 전에** 적용된다 |
| `--from-stage {magi,read,merge,cast,translate,validate,render}` / `--only` | 단계 지정 |
| `--styleguide PATH` | 작품 단위 시트를 물려 쓴다 |
| `--no-resume` | 끝난 단계도 다시 |
| `--no-manage-router` | 라우터를 파이프라인이 죽였다 살리지 않는다 |

기본으로 파이프라인이 **라우터를 직접 관리**한다: Magi 전에 내리고 판독 직전에 올린다. Magi(PyTorch)와 llama-server 가 같은 VRAM 을 두고 충돌해 OOM 이 났기 때문이다. `/models/unload` 엔드포인트도, 자식 프로세스만 죽이는 것도 VRAM 을 반환하지 않아서 프로세스를 내리는 방식으로 갔다.
> 새 GPU 는 64GB 라 이 강제 재기동이 더는 필요 없을 수 있다. §9 참조.

## 4. 실측 수치 (전부 재현된 값)

### 판독 정확도 — Pepper&Carrot ep11, 공식판 정답 대조

| | 매칭 | 완전일치 | 문자 정확도 |
|---|---|---|---|
| VLM 크롭 패스 (전체) | 90% | 30/35 (86%) | 93.9% |
| **VLM 크롭 패스 (후원자 명단 p7 제외)** | **94%** | **88%** | **98.0%** |
| VLM 페이지 패스 | 90% | 27/35 (77%) | 93.4% |
| manga-ocr (전체 / p7 제외) | 79% / 89% | 71% | 94.4% |

**매칭률 정의:** `짝지어진 정답 말풍선 / 전체 정답 말풍선`. 분모가 우리 출력이 아니라 **정답**이고, 글자 유사도 0.25 이상일 때만 짝이 지어진다 → 출력이 있어도 내용이 틀리면 매칭 실패다.

**후원자 명단 페이지가 지표를 4%p 왜곡하고 있었다.** 채점·처리 양쪽에서 제외해야 한다.

### 판독 모델 비교 — 동일 박스·프롬프트·스키마·정답

| 모델 | 매칭 | 완전일치 | 문자 정확도 | 소요 |
|---|---|---|---|---|
| **Qwen3.6-35B-A3B Q4_K_M (채택)** | 90% | 27/35 (77%) | 93.4% | **134s** |
| Qwen3.8-27B **ABLITERATED** Q6_K | 90% | 18/35 (51%) | **81.3%** | 523s |
| Qwen3.8-27B HauhauCS Uncensored Q6_K_P | 90% | 27/35 (77%) | 93.2% | 447s |
| Qwen3.8-27B unsloth UD-Q6_K_XL | 90% | 28/35 (80%) | 93.0% | 455s |
| Qwen3.8-27B unsloth UD-Q4_K_M | 85% | 29/33 (88%) | 97.6% | 470s |

**결론 두 가지 — 둘 다 이전 가설을 뒤집었다.**

1. **문제는 Qwen3.8 이 아니라 ABLITERATED 빌드였다.** 희귀 한자 표류(`恺`·`胰`·`訙`)와 전사 대신 의역은 모델 성질이 아니라 **가중치 수술(abliteration)의 부작용**이다. uncensoring 자체는 무해했다(HauhauCS 93.2% ≒ unsloth 원본 93.0%).
2. **양자화는 이 작업에 영향이 없다.** 같은 unsloth 계열에서 **Q4 가 Q6 보다 높았다**(97.6% vs 93.0%). "양자화가 CJK 글자 판별을 해친다"는 가설은 서로 다른 두 계열에서 반증됐다.

→ **판독은 Qwen3.6 유지.** 정확도 동급인데 3.5배 빠르다.

### 단계별 소요 (ep11 7페이지)

| 단계 | 일반 | `--fast` |
|---|---|---|
| ① Magi | ~10s | ~10s |
| ② 페이지 판독 | 134s | 134s |
| ② 크롭 전사 | 123s | **5s** |

### 기타

## 5. 말투(register) 처리 — 이 프로젝트의 심장

### 원문 증거가 모델 추론을 이긴다

`vlm/register_cues.py` 가 화자별 경어/평어 표지를 **원문에서 세어** 시트 프롬프트에 권위 있는 관찰로 주입한다.
Gemma 가 메이드에게 평어를 배정하며 "나이·지위가 비슷하다"고 사회적 추론을 했는데, 정작 원문엔 `参りました`·`ございます`·`お導きいただけます` 가 있었다. 개수를 주입하니 한 번에 고쳐졌고, 모델이 스스로 그 증거를 근거로 인용했다.

**일관성 검사는 잘못된 시트를 잡지 못한다** — 출력이 시트와 맞는지만 보므로, 확신을 갖고 틀린 시트는 위반 0으로 통과한다. 그래서 증거 검사가 별도로 존재한다.

### 결정론적 종결어미 분류 — 오탐 제거 5라운드의 산물

전부 실제 버그였다:

- `합니다` 는 조합된 음절 — `습니다|ㅂ니다` 매칭은 놓친다. `니다$` 로 잡을 것
- `니까` 는 중의적(`갑니까` 격식 vs `괜찮으니까` 연결) — 앞 음절 종성이 ㅂ인지로 가른다
- 연결어미(`-고`,`-지만`,`-도록`), 조사 종결(`여러분도`), 호격(`클로에 씨`), 한글 2자 이하 발화는 **말투 정보가 없다**. 만화는 한 문장을 말풍선 여러 개로 쪼갠다
- **경어↔평어 표류만** 잡는다. 경어 안에서 합니다체/해요체가 섞이는 건 정상 한국어
- `kind == "thought"` 는 건너뛴다. 독백은 수신자가 없고, 정중한 인물의 하다체 속말은 옳다
- `아`/`야` 를 호격 표지로 보면 안 된다 — 흔한 평어 종결 `거야` 와 충돌

### 재요청 루프

`temperature 0` 은 그리디라 같은 프롬프트에 같은 출력이 온다 → 라운드가 정체된 건 모델 한계가 아니라 그 때문이었다. **라운드마다 온도를 올리고 라운드 고유 넛지와 위반 코드별 지시를 준다.** 그리고 **위반 수를 엄격히 줄이지 못한 수정은 되돌린다** — 한 번은 `다 됐어~` 가 `出来了よ~` 로 바뀐 적이 있다.

### `--harsh` (LLM 판정자) — opt-in, 아직 미검증

작성 기억이 없는 새 컨텍스트에서 돌린다(사용자 제안, 타당하다). 깨끗한 챕터에서 3건이 나왔는데 **전부 노이즈**였고 둘은 자기 텍스트 안에서 자가당착이었다. 인용된 `requirement` 를 요구하면 노이즈가 눈에 보여 버릴 수 있다. 결정론적 검사가 항상 우선한다. **정규식으로 못 보는 진짜 오류가 있는 챕터에서 한 번 재보고 존폐를 정하기로 했다 — 미실행.**

| `vlm/read_page.py` | 파싱 실패 시 토큰 예산 2배로 1회 재시도 → 그래도 실패하면 `read_skipped` 로 확정하고 통과 |
| `vlm/build_cast.py` | 별칭 검증 — 화자로 등장한 적 없는 라벨 자동 제거 (`cat` 오병합 방지) |
| `vlm/validate_translation.py` | 옛 시그니처 `ask(session,url,…)` 로 호출하던 3곳 배선 (자동 수정이 죽어 있었다) |

**`work/maid2_full/` (77페이지 중국·일본어 혼재)** — `magi.json` → `page.json` → `crop.json` → `merged.json` → `cast.json` → `styleguide.json` 까지 산출됐고 **번역 이후는 미실행**(`out/` 비어 있음). 재개하면 `--from-stage translate` 부터다.

### 마지막에 잡은 결함들 (참고)

- **글자 겹침** — 세로쓰기 원문에서 Magi 가 한 말풍선의 열들을 별개 박스로 잡는데, 말풍선 검출이 박스마다 독립적으로 돌아 둘 다 같은 말풍선을 반환했다(겹침 92%, 99%). 서양식 가로 레이아웃(ep11)에서는 말풍선당 박스가 하나라 드러나지 않았던, **말풍선 확장 기능이 만든 회귀**다.
- **한 페이지 실패가 77페이지를 막았다** — 1441초를 쓰고 결과를 못 받았다. p33은 박스 1개(118×149, 대사 아님)뿐인 사실상 빈 페이지였고 응답이 52자에서 끊겼다(토큰 예산 문제가 아니라 모델 조기 종료). 지금은 두 번 실패하면 `read_skipped` 로 통과시킨다.
- **`--skip-pages` 적용 시점이 병합 단계였다** → 후원자 명단 페이지를 판독까지 다 하고 거기서 토큰 한도를 넘겨 전체가 멈췄다. 판독 **전**으로 옮겼고 한도도 4096→8192 로 올렸다.
- **설정 이원화** — `.ini` 에만 모델을 추가했더니 라우터는 인식하는데 파이프라인이 거부해 판독 3건이 통째로 날아갔다. → `tools/sync_models.py`

## 7. 미해결 — 우선순위 순

### 1) 작품 단위 누적이 검증에 **실패**했다 (설계의 핵심 주장)

ep11 시트를 ep13 에 물려 봤더니 세 가지가 드러났다:

- **겹치는 인물이 `Pepper` 하나뿐.** ep13은 다른 인물이 나오는 편이라 시트가 채워주는 게 거의 없었다. 그 `Pepper` 조차 대사 1개라 표본이 안 된다
- **물려받은 시트 자체가 손상돼 있었다** — 전원 `casual`, 전 관계 `반말`. 수정 전 시트는 페퍼→교모 `하십시오체/해요체`, 교모→페퍼 `해라체/하게체` 로 정확했고 원문 증거(`教母様`, `じゃ·ぞ·のじゃ`)까지 인용했었다. **원인은 "시트 중복 해소" 변경**: `SETTLED CAST` 블록을 프롬프트 앞에 넣으면서 말투 지시의 비중을 밀어냈다. 게다가 폐기했어야 할 임시 라벨(`cat`,`old man`,`pirate girl`)이 `registerTo` 에 남아 있었다
- **안전망이 한쪽 방향으로만 작동한다** — `register_cues.contradictions()` 는 원문 증거가 **있는** 인물만 지킨다. 이 챕터에서 검출된 증거는 `Mother Superior = plain` 하나뿐이었고, 정작 틀린 페퍼(경어여야 함)는 증거가 없어 검사 대상이 아니었다

→ 재개 시 **가장 먼저 손볼 것.** 시트 프롬프트 구조를 되돌리거나, 확정 인물 목록을 말투 지시 **뒤**에 두는 것부터.

### 2) 77페이지 규모에서 화자 파편화

명부에 라벨 19개. `silver-haired maid`(311대사)와 `maid`(101대사)가 별개, `man`/`male`/`male partner`, `dark-haired maid`/`black-haired maid` 도 마찬가지. `build_cast` 가 정규화하도록 만들었지만 **1441초 분량의 전사가 챕터 단위 텍스트 패스에 들어가는지, 들어가도 19개 라벨을 제대로 정규화하는지 미검증**이다. ep11 이 38박스였으니 691박스는 18배다.

### 3) 말풍선 검출 실패 23%

허용치 사다리로 73%→77%까지만. 실패하면 글자 크기를 부당하게 누른다. **세그멘테이션 실험이 후보** — 사용자 제안이고, 비직사각형 말풍선을 정확히 딸 수 있다. 다만 말풍선 없는 대사(독백·그림 위 글자)에서 페이지 전체로 번지는 오인페인팅이 우려된다(현재 flood fill 도 넓이로 판정해 버린다).

### 4) ④ 인물·스토리 213초 — think on/off 비교

최대 병목. 텍스트 전용인데 추론이 켜져 있다. 시트 생성이 417초 걸린 것도 같은 원인.

## 11. CLI 개편 · 결함 수정 — 2026-08-23 (2차)

### `--fast` → `--transcribe`, 그리고 `--thinking`

`--fast` 는 **무엇이 빨라지는지가 이름에 없었다.** 실제로 하는 일은 크롭 전사를
manga-ocr 로 바꾸는 것이다. 그리고 일본어 전용이라는 제약이 이름에서 안 보였다.

| 옛것 | 새것 |
|---|---|
| `--fast` | `--transcribe ocr` (옛 이름은 경고를 내며 계속 동작) |
| (없음) | `--transcribe vlm` — 기본값 |
| (없음) | `--thinking {auto,on,off}` |
| (없음) | `--model-read NAME` / `--model-text NAME` |

`--thinking` 이 필요한 이유: 단계 스크립트마다 추론 플래그의 **이름과 기본값이 다르다.**
`read_*` 와 번역은 `--thinking` 으로 켜고(기본 꺼짐), cast 와 시트는 `--no-thinking` /
`--no-sheet-thinking` 으로 끈다(기본 켜짐). 그 차이는 의도적이지만 부르는 쪽이 외울 일은
아니다. `pipeline.py` 의 `THINKING` 표에서 한 축으로 옮긴다.

- `auto` — 단계마다 맞는 기본값 (추출은 끄고, 인물·시트는 켠다). 지금까지의 동작.
- `on` / `off` — 전 단계 강제. 과사고를 재려면 같은 소재를 `off` 로 다시 돌려 비교한다.

`--model-read` / `--model-text` 는 한 실행에서만 모델을 바꿔 보기 위한 것이다. 영구히
바꾸려면 `config/models.ini` → `tools/sync_models.py` → `config.json` 의 `stages`.

### 글자 겹침 — 원인은 임계값이 아니었다

`out/02_ko.jpg` 첫 패널에서 두 대사가 포개져 찍혔다. 좌표를 찍어 보니:

```
id=0  원본 y 159–341   확장 후 132–544
id=1  원본 y 421–600   확장 후 372–616     → 겹침 0.41
```

**원본 박스는 멀쩡히 떨어져 있는데 말풍선 확장이 서로를 침범했다.** 말풍선 둘이 맞닿아
있으면 flood fill 이 이웃까지 흐른다. 기존 `split_shared_rects` 는 겹침 0.5 이상만 보므로
0.41 은 그대로 통과했다.

임계값을 0.4 로 내리는 것은 답이 아니다 — 그건 **한 말풍선**을 나눠 받은 경우를 위한
함수이고, 여기는 남의 말풍선을 침범한 경우라 처리 방법 자체가 다르다. 둘을 갈랐다:

- `separate_neighbours()` — 원본끼리 안 겹치는데 확장만 겹치면(0 < ov < 0.5), **두 원본
  사이 중간에 경계를 긋는다.** 원본만큼은 언제나 남긴다(Magi 좌표가 픽셀 정확하므로).
- `merge_shared_bubbles()` — 원본까지 사실상 같은 자리면(ov ≥ 0.5) **한 문단으로 합친다.**
  §7-5 가 요구하던 것이다. 위아래로 나누면 몫이 좁아져 말풍선 확장의 이득이 상쇄되고
  몫이 모자라면 넘쳤다. 합치면 말풍선 전체를 한 문단이 쓴다 — 원문이 그 말풍선을 다
  쓰고 있었으므로 들어갈 자리는 원래 있다.
  옛 동작은 `--shared-bubble split` 로 남겨 뒀다.

ep11_cn 재조판으로 확인: 겹침 소멸, 넘침 0, p07·p08 에서 합침 1건씩 발생하고 결과가
말풍선을 제대로 채운다.

**아직 확인 못 한 것:** §7-5 의 원래 동기였던 **세로쓰기 다열 케이스**다. ep11 은 가로쓰기라
`merge_shared_bubbles` 가 다른 경로(이웃 침범 해소 후 잔여 겹침)로만 발동했다. maid2 처럼
Magi 가 한 말풍선의 열을 별개 박스로 잡는 소재에서 다시 봐야 한다.

### 호출 사용량 계측

`vlm/backend.py` 의 `Client` 가 응답의 `usage` 를 누적하고, `read_texts` ·`build_cast` ·

## 12. 긴 챕터에서 터진 두 곳 — 2026-08-23 (3차)

77페이지(대사 692줄) 챕터를 돌리자 ④에서 죽었다:

```
json.decoder.JSONDecodeError: Unterminated string starting at line 2334 (char 26228)
```

원인은 **출력이 챕터 길이에 비례**하는 곳이 두 군데 있었다는 것이다. 입력은 문제가
아니다 — 전사 32K자는 ctx 65536 에 넉넉히 들어간다. 망가진 건 출력이다.

### ④ cast — 줄여서 해결

`reassign` 을 "speaker 를 바꿔야 하는 **모든** key" 로 받고 있었다. 항목 수가 대사 줄
수를 따라가 692줄에서 26,228자에 잘렸다.

그런데 **그 목록은 없어도 된다.** 코드가 이미 `alias_to_id`(별칭 → 확정 id) 사전으로
모든 줄을 기계적으로 덮고 있었고, `reassign` 은 그 위에 얹히는 우선값일 뿐이었다.
모델이 할 일은 별칭을 묶는 것(인물 수만큼)이지 줄마다 답을 쓰는 것이 아니다.

→ `reassign` 은 **기계적 치환이 틀리는 줄만** 받는다. 읽는 곳이 없던 `pages`
(페이지마다 등장 인물)도 뺐다. 이제 출력은 O(인물 수)다.
ep11_cn 재확인: cast 출력 **466 토큰**, 라벨 정규화 정상.

### ⑤ translate — 나눠서 해결

이쪽은 줄일 수 없다. **모든 대사의 번역문이 결과에 있어야** 한다. 692줄이면 3만
토큰이 넘는데 예산은 8192 였다.

나눠도 말투가 흔들리지 않는 것이 2단 구조의 요점이다 — 인물별 말투는 **시트에 이미
확정돼 있고** 배치마다 그 시트를 통째로 준다. 배치가 정하는 것은 문장이지 말투가 아니다.
직전 배치의 끝 6줄을 "번역하지 말 것" 맥락으로 붙여 흐름을 잇는다.

`--batch-lines 60`(기본), `--batch-overlap 6`. 실측 확인:

| ep11_cn 34줄 | 호출 | 응답 | 말투 일치 |
|---|---|---|---|
| 단일 배치 (기존과 동일) | 1 | 34/34 | 14/17 (82%) |
| 5배치 (`--batch-lines 8`) | 5 | 34/34 | 16/19 (84%) |

**쪼개도 말투 오류는 3개로 같다.** 설계 주장이 실측으로 확인됐다.

### backend — 잘린 응답을 알아보게

두 실패는 증상도 대처도 다른데 하나로 뭉쳐 있었다.

| | 증상 | 대처 |
|---|---|---|
| `EmptyResponse` | 추론이 예산을 다 먹어 `content` 가 빔 | 추론 끄고 1회 재시도 (이미 있었음) |
| **`TruncatedResponse`** | 출력 자체가 예산보다 커서 잘림 | **예산 2배로 1회 재시도 (추가)** |

구분하지 않으면 잘린 JSON 이 그대로 `json.loads` 로 들어가
`Unterminated string starting at line 2334` 같은, 원인을 전혀 알려주지 않는 예외가 난다.

### 남은 같은 위험

⑥ 재요청도 위반 박스를 한 요청에 모아 보낸다(`max_tokens` 8192). 위반이 많은 챕터에서는
잘릴 수 있다. 다만 `try/except` 로 감싸여 있어 파이프라인을 죽이지 않고 그 라운드만
건너뛰며, 이제 백엔드가 예산 2배로 한 번 재시도한다. 실제로 문제가 되면 ⑤와 같은 방식으로
나누면 된다.

## 13. 스키마에 상한이 없으면 붕괴를 막을 수 없다 — 2026-08-23 (4차)

§12 를 고친 뒤에도 77페이지 챕터가 ④에서, 그다음 ⑤에서 또 죽었다. 이번엔 예산도
출력 개수도 아니었다 — **문자열 하나가 17,000자를 넘겼다.**

### 무엇이 일어났나

JSON 문법은 다른 자리에서는 모델을 강하게 제약하지만 **열린 문자열 안에서는 아무
제약도 하지 않는다.** 게다가 문법 때문에 JSON 중간에 EOS 를 낼 수도 없다. 그래서
헷갈린 모델이 갈 수 있는 유일한 방향이 "문자열을 계속 늘리는 것"이 된다.
상한 없는 문자열은 사실상 **함정**이다.

여기에 두 가지가 겹쳤다. `temperature 0`(그리디)은 같은 토큰이 계속 최고 확률을
받으면 빠져나올 길이 없고, 692줄이 전부 같은 꼴인 16K 토큰짜리 입력은 반복을
유도한다. 원래 설계가 상정한 규모(66박스, 1.5K 토큰)의 20배다.

### 어디였나 — 전면 붕괴가 아니었다

상한을 채운 뒤 같은 챕터를 다시 돌려 길이만 재봤다:

| 필드 | 개수 | 최대 길이 | 상한 도달 |
|---|---|---|---|
| id | 6 | 16자 | 0 |
| aliases | 14 | 18자 | 0 |
| evidence | 6 | 72자 | 0 |
| **notPeople** | **60 (= maxItems)** | **80자 (= maxLength)** | **양쪽 다** |

붕괴는 **`notPeople` 한 필드**에서만 일어났다. 모델이 그걸 쓰레기통처럼 쓰면서
항목을 계속 뱉었고 그중 하나의 문자열이 끝없이 늘어났다. 다른 필드는 전부 멀쩡했다.

### 고친 방법 — 필드별이 아니라 훑어서

처음에는 `evidence`(400)와 `story`(1500)만 막았다. 그랬더니 `id`·`aliases`·
`notPeople`·`reassign.speaker` 가 뚫렸다. **빠뜨린 하나가 곧 같은 사고다.**

`backend.bound_schema()` 가 스키마를 훑어 상한 없는 문자열에 `maxLength`,
상한 없는 배열에 `maxItems` 를 채운다. 명시한 값은 보존한다. 다섯 스키마
(`CAST` `STYLEGUIDE` `TRANSLATION` `RESPONSE` `JUDGE`) 전부에 적용했다.
번역문처럼 길어야 하는 필드는 스키마에 직접 값을 적어 둔다(`target` 600자).

**llama.cpp 가 실제로 강제하는지 확인했다.** `maxLength: 10` 을 주고 긴 글을
요청하면 정확히 10자에서 끊긴다. `maxItems: 2` 를 주면 인물 6명짜리 챕터에서
정확히 2명이 나온다. 프롬프트의 부탁이 아니라 디코딩 제약이다.

효과: 같은 챕터의 ④가 **49,152 토큰을 태우고 실패 → 1,207 토큰으로 15초 만에
성공**. 상한이 루프를 끊자 모델이 곧바로 정상 출력으로 복귀했다.

### 재개가 재개를 무효화하던 문제

§12 에서 넣은 `--fill-from` 재개가 **채울 것이 없어도 crop.json 을 다시 썼다.**
mtime 이 밀리니 `is_fresh` 가 "입력이 새로워졌다"고 보고 병합·인물·번역을 통째로
다시 돌렸다. 끝나 있던 ④가 다시 돌아 터진 것이 그 때문이다.
출력 경로와 `--fill-from` 경로가 같고 채울 것이 없으면 이제 **파일을 건드리지 않는다.**

### 남은 확인 필요

77페이지 챕터에서 `라벨 변경 660줄 / 유지 32줄` — 95%가 재배정됐다(ep11 은 절반).
인물 6명으로 수렴한 것이 맞을 수도 있고 §7-2 가 경고한 **과병합**일 수도 있다.
소재가 `assets/secrets` 파생이라 사람이 봐야 한다.

### 2 — 지워지지 않은 원문 (가설)

`render/make_mask.py` 의 `mask_for_box(img, bbox, 0.12, 12, 0.35, 3, 5)` 가 획을
연결요소로 잡아 지운다. 남는 경우로 짐작되는 것:

- **원문 획이 Magi 박스 밖으로 삐져나온다.** 마스크는 박스 안만 본다. 세로쓰기의
  긴 꼬리나 요음·촉음이 경계에 걸리면 남는다 → 마스크 전용 여유(pad)를 조판용
  여유와 따로 두는 것이 후보
- **대비 부족.** 배경이 회색이거나 그림 위에 얹힌 글자는 임계값을 못 넘긴다.
  §7-3 의 말풍선 검출 실패(23%)와 원인이 같은 계열이다
- 확인 방법: 마스크 비율이 유난히 낮은 페이지를 골라 마스크만 따로 저장해 본다

### 3 — 너무 작은 글자 (가설)

`fit_at_base` 는 챕터 기준 글자 크기에서 시작해 **자리에 안 들어가면 줄인다**
(`--min-font 11` 까지). 자리가 좁아지는 경로가 둘이다:

- **말풍선 검출 실패** → 확장이 안 되고 Magi 박스(원문에 딱 붙은 크기)를 그대로
  쓴다. 한국어가 원문보다 길면 줄일 수밖에 없다. **§7-3 이 그대로 여기로 이어진다**
- **`separate_neighbours` 가 자리를 잘라낸 경우.** 이웃 침범을 풀면서 세로로
  나눴는데 그 몫이 원래 박스보다 크게 넓지 않으면 이득이 없다

확인 방법: 조판 로그에 **실제 사용된 글자 크기**를 찍고, 챕터 기준값 대비 얼마나
줄었는지 분포를 본다. 지금은 넘침 여부만 나온다.
